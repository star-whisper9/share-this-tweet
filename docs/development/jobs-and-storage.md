# 后台任务与存储

队列由 `background/export-jobs.ts` 管理，使用 Manifest V2 的持久后台页执行。内容脚本负责提交，后台负责处理和保存；任务页只读取状态并发起操作，不能成为任务唯一的执行宿主。

持久后台页仍受浏览器和系统生命周期限制。它能让任务在原推文关闭后继续运行，但不能保证浏览器退出或 Android 回收进程后继续编码。

## 入队与执行

`ExportJobRequest` 固定推文、媒体选择、设置、主题、语言和本次是否强制执行。后台完成请求校验后，先将任务写入 IndexedDB，再返回入队成功。同一个任务 ID 允许重复提交相同请求，收到不同请求时会拒绝，避免重试通信产生重复任务。

队列一次处理一个任务，渲染入口为 `renderExportJob`。生成文件通过 `onFile` 交回队列，先落入任务缓存，再发起下载。数据库写入失败不能返回已入队或已保存成功。

进度、诊断、文件写入、取消和清理可能相互竞争。队列通过串行的 `mutateJob` 修改元数据，用草稿提交数据库，成功后再替换内存记录；`background/job-updates.ts` 汇集渲染回调。新增状态更新时沿用这些入口，不直接改 Map 中的对象绕过事务，否则进度可能覆盖取消，或内存状态领先于数据库。

## 任务状态与文件状态

| 任务状态      | 含义                                         |
| ------------- | -------------------------------------------- |
| `queued`      | 已持久化，等待处理                           |
| `running`     | 正在处理或等待本次保存完成                   |
| `ready`       | Android 已生成文件，仍有文件等待用户发起保存 |
| `completed`   | 本次任务完成；保存含义仍需按平台区分         |
| `limited`     | 触发可放宽的处理保护，且尚无文件输出         |
| `partial`     | 处理或保存遇到错误，任务已有文件可保留       |
| `failed`      | 处理或保存失败，且尚无文件输出               |
| `cancelled`   | 用户取消                                     |
| `interrupted` | 后台重启时发现任务原先仍在运行               |
| `expired`     | 待保存任务的必要文件缓存已失效               |

每个文件另有 `saved`、`cached`、`cacheExpiresAt` 等字段。`partial` 和 `limited` 的原因写入 `warnings`，界面筛选和批量保存依据文件保存状态。能生成替代文件的动态处理会完成正常的保存流程，同时附上回退原因及 `canForceRetry`。

启动时将原来的 `running` 标记为 `interrupted`，排队任务继续执行。

### 普通重试与强制重试

普通重试允许 `failed`、`limited`、`partial`、`cancelled`、`interrupted` 和 `expired` 重新排队。任务沿用原 ID 和请求，保留已保存文件的元数据，清除待重新生成的文件、旧诊断和警告。渲染从头运行，`acceptFile` 用稳定的文件 ID 跳过此前已保存的输出。

有 `canForceRetry` 的非活动任务可通过 `export-job-force-retry` 克隆原请求，生成新的任务 ID 并写入 `force: true`。原任务和输出继续保留，新任务重新处理原请求中的全部内容，因此可能再次保存成功项。可放宽的保护与仍执行的校验详见[导出与媒体处理](media-processing.md#保护限制与强制执行)。

## 桌面与 Android 的保存差异

### 桌面

队列创建 Blob URL，调用浏览器下载 API，再由 `core/download-monitor.ts` 等待下载真正完成，之后才设置 `saved` 并释放文件缓存。调用 `downloads.download` 得到下载 ID，只说明请求已创建。

下载等待最多 30 分钟，超时后尝试取消并暴露错误；取消失败会保留警告。保存失败时生成文件仍在缓存中，任务页可以手动补存。Blob URL 在结束时撤销，取消要传播到网络、渲染和当前下载。

### Android

任务入队时打开或复用独立任务页，后续提交不抢到前台。生成后由任务页取得 Blob，调用保存，再通知后台更新文件状态。

Android 的 `saved` 代表已经发起保存请求，扩展无法确认最终落盘或用户是否取消。因此界面使用「已发起下载」语义，缓存还需额外保留 24 小时。不要把这一步改成与桌面相同的「已确认保存」判断。

### 部分成功与来源记录

多项媒体分别尝试处理，已有输出不会因后续一项失败而消失。保存后，队列尝试写入来源与输出记录；如果文件已经保存、来源记录写入失败，应显示警告，不能将已完成的下载描述为未保存。

复制文字也可能已经写入剪贴板，但来源记录保存失败。修改错误处理时保留实际结果与附带记录失败之间的区别。

## 三类持久数据

| 存储                                     | 内容                                | 实现                                         |
| ---------------------------------------- | ----------------------------------- | -------------------------------------------- |
| `browser.storage.local`                  | 偏好设置和界面语言，无媒体二进制    | `shared/settings.ts`                         |
| IndexedDB `share-this-tweet`             | 推文来源记录与输出说明，无媒体 Blob | `core/storage.ts`、`shared/storage-model.ts` |
| IndexedDB `share-this-tweet.export-jobs` | 任务快照、输出文件和诊断            | `core/job-store.ts`                          |

来源记录是用户管理的归档，不随任务缓存到期删除。来源记录导出为带 `schemaVersion` 的 JSON；导入先校验，再在同一事务中写入推文和输出说明。它不是设置备份，也不是媒体备份。

## 任务数据库结构

当前任务数据库版本为 `2`：

| object store  | 保存的数据                                     |
| ------------- | ---------------------------------------------- |
| `jobs`        | 请求快照、摘要和文件元数据                     |
| `files`       | 文件 Blob，以文件 ID 为键，并按 `jobId` 建索引 |
| `diagnostics` | 按任务 ID 保存诊断报告                         |

队列初始化和列表读取只加载任务元数据，文件与诊断按需读取。不要为显示文件大小或刷新进度，把整批 Blob 重新载入内存。

`putExportJob` 将元数据修改、文件增加／移除和诊断修改放在同一事务中。删除任务按 `jobId` 索引清除关联文件，避免留下孤立 Blob。来源数据库删除推文关联输出时也使用索引，而不是每次扫描全部输出。

### 修改 schema 与迁移

从旧版任务数据库迁移时，在升级事务内按游标逐条拆分内嵌 Blob 与诊断，失败由事务回滚。桌面已保存文件不再迁移媒体缓存；其他文件和任务从升级时获得完整保留期限。

后续结构变化需要增加数据库版本、处理已有数据，并在升级事务中维持一致性。不能删除旧数据库后重新创建，也不能先向界面宣布迁移完成再异步补写文件。数据库打开、请求和事务完成都可能失败，需要观察各自的错误。

## 过期与显式清理

期限由 `shared/job-retention.ts` 定义，任务数据库存储每份文件的到期时间：

| 内容                     | 当前期限             |
| ------------------------ | -------------------- |
| 桌面已确认保存的文件缓存 | 立即释放             |
| 桌面未保存的生成文件     | 24 小时              |
| Android 已发起保存的文件 | 从发起保存起 24 小时 |
| Android 未发起保存的文件 | 7 天                 |
| 诊断                     | 最后更新后 7 天      |
| 已结束任务与快照         | 结束后 30 天         |

启动、列出任务或提交任务会触发清理检查，后台另每 15 分钟清理一次。浏览器退出期间不运行，下一次启动补清。清理跳过排队、处理和正在保存的任务，并与状态修改使用同一串行路径。

手动清除缓存只删除已结束任务的文件与诊断，保留元数据；清除任务历史连同元数据一起删除。两者针对全部已结束任务，不受列表筛选影响，不删除来源归档和设备上的下载文件。

当前没有总容量硬上限，短期大量生成未保存视频仍可能触及浏览器配额。增加容量策略前，需要明确允许删除哪些尚未到期的输出，不能静默清空用户未保存的文件。

## 修改与验证

队列行为主要由 `export-jobs`、`job-renderer`、`job-client` 和 `background-download` 测试覆盖；事务、迁移与缓存边界见 `job-store`、`storage`、`storage-database`；筛选和批量文件选择见 `job-list`。文件均位于 `tests/<名称>.test.ts`。

存储测试使用 fake-indexeddb，可以验证事务与迁移的数据结果，不能证明 Firefox 已立即归还磁盘空间。修改相关行为后，人工检查：

1. 提交后关闭原推文，任务仍继续；重载扩展后运行中的任务转为已中断，手动重试不重复下载成功项。
2. 多项输出中一项失败，任务显示部分完成。确认已有文件可以保存，普通重试会跳过已保存项。
3. Android 连续提交、批量发起、取消一次保存及再次保存，核对实际下载目录。
4. 升级已有任务数据，再清除缓存或历史；活动任务、来源归档和设备文件保持符合各自契约。
5. 对产生替代文件的超限任务执行强制重试，确认新任务另行排队，原任务及文件仍可查看。
